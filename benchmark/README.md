# ICN Benchmark Framework

Reproducible benchmarking pipeline for the ICN simulation project.
Wraps `app/run_experiments.py` — the simulator and blockchain logic are
**not modified** by this pipeline.

---

## Prerequisites

| Requirement | Why |
|---|---|
| Python environment with `app/requirements.txt` installed | Scripts import matplotlib, pandas, numpy |
| `matplotlib`, `pandas`, `numpy` additionally in env | Analysis and graph scripts |
| Fabric stack running (`docker compose up -d` from repo root) | Required for `with_auth` runs |

Install extra dependencies if needed:
```bash
pip install matplotlib pandas numpy
```

---

## Quick Start

```bash
# From repo root — all three commands, in order:
python benchmark/scripts/run_benchmarks.py
python benchmark/scripts/analyze_results.py
python benchmark/scripts/generate_graphs.py
```

Fabric must be running before the first command. Check status:
```bash
docker compose ps          # orderer, peer0, bootstrap should be healthy/exited-0
```

To run without Fabric (without_auth modes only):
```bash
python benchmark/scripts/run_benchmarks.py --skip-auth
```

## Pipeline Steps

### Step 1 — `run_benchmarks.py`

Runs `app/run_experiments.py` four times, once per mode combination:

| Mode label | chunking | auth |
|---|---|---|
| `without_chunking__without_auth` | off | off (in-memory ledger) |
| `without_chunking__with_auth` | off | on (Fabric gRPC) |
| `with_chunking__without_auth` | on | off |
| `with_chunking__with_auth` | on | on |

Each run uses `--iterations 5` by default (configurable). Timing is measured
with `time.perf_counter()` around each subprocess call.

Outputs written to `benchmark/data/raw/`:
- `benchmark_config.json` — parameters + timestamp
- `benchmark_timing.csv` — wall-clock seconds per mode
- `{mode}/raw_results.csv` — per-row measurements
- `{mode}/summary_by_publishers.csv`
- `{mode}/summary_by_users.csv`
- `{mode}/iteration_profile_by_publishers.csv`
- `{mode}/iteration_profile_by_users.csv`

CLI options:
```
--iterations N          Topology seeds per mode (default 5)
--publisher-start N     (default 4)
--publisher-end N       (default 10)
--user-start N          (default 2)
--user-end N            (default 8)
--skip-auth             Skip with_auth runs (Fabric not required)
```

### Step 2 — `analyze_results.py`

Merges the four mode raw outputs and derives additional datasets.

Outputs written to `benchmark/data/processed/`:

| File | Contents |
|---|---|
| `all_raw.csv` | All four mode combos concatenated (single CSV) |
| `summary_by_publishers.csv` | Mean ± std per (chunking, auth, Np, LMM) |
| `summary_by_users.csv` | Mean ± std per (chunking, auth, Nu, LMM) at max Np |
| `lmm_comparison_publishers.csv` | LMM-1 vs LMM-2 — with_chunking/with_auth only |
| `lmm_comparison_users.csv` | Same, by user count |
| `chunking_impact.csv` | with/without chunking — LMM-2, with_auth |
| `failure_rates.csv` | failure_rate = 1 − avg_success_rate |
| `effective_throughput.csv` | derived: Nu × avg_success_rate / arrival_window |
| `benchmark_timing.csv` | Copy of raw timing measurements |

### Step 3 — `generate_graphs.py`

Reads processed CSVs and produces 10 figures × 3 formats (PNG, PDF, SVG) = 30 files.

## Graph Descriptions

### Figure 1 — `fig01_lmm_delay_vs_publishers`
**Research question:** Does LMM-2 multipath routing achieve lower average delay
than LMM-1 single-best-path as the publisher count grows?

- X: Number of publishers (Np = 4, 6, 8, 10)
- Y: Average simulated delay (hop-count based; units are simulation time steps)
- Lines: LMM-1 (blue) vs LMM-2 (orange), error bars = ±1 std dev
- Source: `lmm_comparison_publishers.csv`

**Note:** Delay is simulated (0.95 × average hops), not wall-clock latency.

---

### Figure 2 — `fig02_lmm_delay_vs_users`
**Research question:** How does user load affect per-algorithm delay?

- X: Number of users (Nu) at the maximum publisher count in the sweep
- Y: Average simulated delay
- Lines: LMM-1 vs LMM-2
- Source: `lmm_comparison_users.csv`

### Figure 6 — `fig06_chunking_impact`
**Research question:** Does multipath chunk distribution (LMM-2) improve latency
or reliability compared to single-path delivery?

- X: Number of publishers (Np)
- Y-left: Average simulated delay
- Y-right: Average success rate
- Lines: with chunking (solid) vs without chunking (dashed), LMM-2, with_auth

### Figure 7 — `fig07_auth_wallclock_overhead`
**Research question:** What is the real-world time cost of adding Hyperledger Fabric
blockchain authentication to the experiment?

- X: Mode combination label
- Y: Total wall-clock time in seconds for the entire benchmark run
- Bars: one per mode combo, colored by mode
- Source: `benchmark_timing.csv`

**Note:** `with_auth` modes include actual gRPC calls to a running Fabric peer
(producer registration, content root storage, Merkle proof verification).
`without_auth` modes use an in-memory simulated ledger with zero I/O.

---

### Figure 8 — `fig08_failure_rate_vs_publishers`
**Research question:** How does request failure rate change across publisher counts
and routing/auth modes?

- X: Number of publishers (Np)
- Y: Failure rate = 1 − avg_success_rate (0–100%)
- Lines: all four (chunking × auth) × 2 LMM combinations = 8 lines
- Source: `failure_rates.csv`

---

### Figure 9 — `fig09_effective_throughput`
**Research question:** Which algorithm and chunking configuration delivers
the highest effective request throughput?

- X: Number of publishers (Np)
- Y: Effective throughput = Nu × avg_success_rate / arrival_window (requests / time unit)
- Lines: LMM-1 / LMM-2, with/without chunking, with_auth only
- Source: `effective_throughput.csv`

**Note:** This is a derived metric computed from measured values — not independently
instrumented. It approximates the rate of successfully completed requests.

---

### Figure 10 — `fig10_iteration_convergence`
**Research question:** How many independent topology seeds are needed for

- Left panel: avg_delay vs iteration number
- Right panel: avg_success_rate vs iteration number
- Lines: one per (LMM × Np) combination
- Source: `with_chunking__with_auth/iteration_profile_by_publishers.csv`

## Metrics Not Available

The following were requested but **cannot be generated** because the simulator
does not instrument them. Extending them would require modifying the application
(outside the scope of this benchmarking layer):

| Metric | Why missing |
|---|---|
| CPU utilization | Not measured anywhere in the codebase |
| Memory utilization | Not measured anywhere in the codebase |
| Per-operation time breakdown (Merkle / gRPC / signature) | Would require instrumentation in `app/fabric_client/client.py` |
| Per-transaction blockchain latency | gRPC calls are not timed inside `app/fabric/chain.py` |
| Cache hit/miss rates | Not tracked in event loop or metrics.py |

## Reproducibility

To reproduce all figures from scratch:

```bash
# 1. Ensure Fabric is up
docker compose up -d

# 2. Run full pipeline
python benchmark/scripts/run_benchmarks.py --iterations 5
python benchmark/scripts/analyze_results.py
python benchmark/scripts/generate_graphs.py
```

The benchmark config is saved as `benchmark/data/raw/benchmark_config.json`
alongside every run. Parameters can be adjusted via CLI flags to `run_benchmarks.py`.

All graphs are generated deterministically from the CSV files in
`benchmark/data/processed/`. No manually edited figures.
